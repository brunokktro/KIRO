Lab 0: Provision the Legacy Environment (EKS + ingress-nginx + sample app)

🎯 Objective

Deploy a complete legacy environment via Terraform: EKS cluster, managed node group, AWS LBC, ingress-nginx controller, and a multi-service sample application with NGINX annotations (URI rewrite, host routing, TLS). After terraform apply, the environment is fully functional and ready for migration labs.

⚡ Prerequisites

  • AWS CLI configured with a named profile (e.g., my-aws-profile)
  • Terraform 1.5+ installed
  • kubectl installed
  • ~15 minutes for provisioning

1Clone the Terraform configuration

# Clone the lab infrastructure
git clone https://github.com/aws-ia/terraform-aws-eks-blueprints.git
cd terraform-aws-eks-blueprints/patterns/nginx

# This pattern provisions:
# - VPC with public/private subnets
# - EKS cluster with managed node group (m5.large x2)
# - AWS Load Balancer Controller
# - ingress-nginx via Helm (with NLB, internet-facing)
# - All required IAM roles and policies
#
# Reference: https://aws-ia.github.io/terraform-aws-eks-blueprints/patterns/network/private-public-ingress/

2Initialize and apply Terraform

# Set your AWS profile
export AWS_PROFILE=my-aws-profile
export AWS_REGION=us-east-1

# Initialize Terraform
terraform init

# Review the plan (~40 resources)
terraform plan

# Apply (takes ~12-15 minutes)
terraform apply -auto-approve

3Configure kubectl

# Get the cluster name from Terraform output
CLUSTER_NAME=$(terraform output -raw cluster_name 2>/dev/null || echo "nginx-migration-lab")

# Update kubeconfig
aws eks update-kubeconfig --name $CLUSTER_NAME --region $AWS_REGION --profile $AWS_PROFILE

# Verify cluster access
kubectl get nodes
kubectl get pods -n ingress-nginx

4Deploy the legacy sample application

Lab 1: Detect and Audit ingress-nginx in Your Cluster

🎯 Objective

Identify all ingress-nginx deployments across your clusters, audit the Ingress resources and annotations in use, and generate a migration inventory.

⚡ Prerequisites

  • kubectl configured with access to your EKS cluster(s)
  • Permissions to list pods, services, and ingress resources across all namespaces

1Detect ingress-nginx pods

# Check all clusters for ingress-nginx
kubectl get pods --all-namespaces \
  --selector app.kubernetes.io/name=ingress-nginx

# Get the controller version
kubectl get deploy -n ingress-nginx \
  ingress-nginx-controller \
  -o jsonpath='{.spec.template.spec.containers[0].image}'
echo

2List all Ingress resources

# List all Ingress resources with their class
kubectl get ingress -A -o custom-columns=\
'NAMESPACE:.metadata.namespace,NAME:.metadata.name,CLASS:.spec.ingressClassName,HOSTS:.spec.rules[*].host'

# Export full Ingress manifests for analysis
kubectl get ingress -A -o yaml > all-ingress-resources.yaml

3Audit NGINX-specific annotations

# Find all unique NGINX annotations in use
kubectl get ingress -A -o json | \
  jq -r '.items[].metadata.annotations // {} | keys[]' | \
  grep nginx | sort -u

# Count usage of each annotation
kubectl get ingress -A -o json | \
  jq -r '.items[].metadata.annotations // {} | keys[]' | \
  grep nginx | sort | uniq -c | sort -rn

4Check for TLS secrets

# List TLS secrets referenced by Ingress resources
kubectl get ingress -A -o json | \
  jq -r '.items[] | select(.spec.tls) | .spec.tls[].secretName' | \
  sort -u

# These will need to be migrated to ACM certificates

✅ Validation

  • You have a list of all clusters running ingress-nginx
  • You know which NGINX-specific annotations are in use (these need mapping to AWS LBC)
  • You have an inventory of TLS secrets that need ACM equivalents
  • You have exported all Ingress manifests for the migration

Lab 2: Migrate Ingress from NGINX to AWS LBC (URI Rewrite + TLS)

🎯 Objective

Migrate a real Ingress resource from ingress-nginx to AWS Load Balancer Controller, implementing URI rewrite and TLS termination with ACM. Based on the official AWS blog walkthrough.

⚡ Prerequisites

  • EKS cluster with an existing node group
  • AWS Load Balancer Controller installed (helm install)
  • AWS CLI, eksctl, kubectl, Helm configured
  • A domain with a certificate in ACM (or use certificate discovery)

1Deploy a sample backend service

# Create a simple echo server
kubectl create deployment http-svc --image=hashicorp/http-echo \
  --port=80 -- -text="Hello from http-svc"
kubectl expose deployment http-svc --port=80 --target-port=5678

2Create the NGINX Ingress (baseline)

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite-nginx
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
  - host: rewrite.bar.com
    http:
      paths:
      - path: /something(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: http-svc
            port:
              number: 80
EOF

3Create the AWS LBC equivalent

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite-alb
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/transforms.http-svc: |
      [
        {
          "type": "url-rewrite",
          "urlRewriteConfig": {
            "rewrites": [
              {
                "regex": "^\\/something\\/(.*)$",
                "replace": "/$1"
              }
            ]
          }
        }
      ]
spec:
  ingressClassName: alb
  rules:
  - host: rewrite.bar.com
    http:
      paths:
      - path: /something
        pathType: Prefix
        backend:
          service:
            name: http-svc
            port:
              number: 80
EOF

4Verify ALB creation

# Check the Ingress status for ALB address
kubectl get ingress rewrite-alb -o wide

# Wait for ALB to be provisioned (1-2 minutes)
kubectl describe ingress rewrite-alb | grep Address

# Test the rewrite
ALB_DNS=$(kubectl get ingress rewrite-alb -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -H "Host: rewrite.bar.com" http://$ALB_DNS/something/test

5Add TLS termination with ACM

# Request a certificate (if you don't have one)
aws acm request-certificate \
  --domain-name rewrite.bar.com \
  --validation-method DNS \
  --region us-east-1

# Get the certificate ARN
CERT_ARN=$(aws acm list-certificates --region us-east-1 \
  --query 'CertificateSummaryList[?DomainName==`rewrite.bar.com`].CertificateArn' \
  --output text)

# Update the Ingress with TLS annotations
kubectl annotate ingress rewrite-alb \
  alb.ingress.kubernetes.io/certificate-arn=$CERT_ARN \
  alb.ingress.kubernetes.io/listen-ports='[{"HTTP": 80}, {"HTTPS": 443}]' \
  alb.ingress.kubernetes.io/ssl-redirect='443' \
  alb.ingress.kubernetes.io/ssl-policy=ELBSecurityPolicy-TLS-1-2-2017-01

6Cleanup

kubectl delete ingress rewrite-nginx rewrite-alb
kubectl delete deployment http-svc
kubectl delete service http-svc

✅ Validation

  • ALB was provisioned and accessible via the DNS name
  • URI rewrite works: /something/test routes to /test on the backend
  • TLS termination works with ACM certificate
  • HTTP-to-HTTPS redirect is active

Lab 3: Convert Ingress to Gateway API with ingress2gateway

🎯 Objective

Use the official ingress2gateway tool to automatically convert existing Ingress resources to Gateway API resources (Gateway + HTTPRoute), then deploy them with AWS LBC v3.

⚡ Prerequisites

  • Go 1.21+ installed (for ingress2gateway)
  • EKS cluster with AWS LBC v3.0+ installed
  • Gateway API CRDs installed in the cluster
  • Existing Ingress resources to convert

1Install ingress2gateway and Gateway API CRDs

# Install ingress2gateway
go install github.com/kubernetes-sigs/ingress2gateway@latest

# Install Gateway API CRDs
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.1/standard-install.yaml

2Export and convert existing Ingress resources

# Export current Ingress resources
kubectl get ingress -A -o yaml > my-ingress.yaml

# Convert using ingress2gateway
ingress2gateway print --providers ingress-nginx \
  --input-file my-ingress.yaml > gateway-resources.yaml

# Review the output
cat gateway-resources.yaml

3Create GatewayClass for AWS LBC

cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: aws-alb
spec:
  controllerName: gateway.k8s.aws/alb
EOF

4Review and adjust converted resources

# ingress2gateway may generate a generic Gateway
# Update the gatewayClassName to aws-alb
# Review any warnings about untranslatable annotations

# Apply the converted resources
kubectl apply -f gateway-resources.yaml

5Verify Gateway and HTTPRoute status

# Check Gateway status
kubectl get gateway -A
kubectl describe gateway my-gateway

# Check HTTPRoute status
kubectl get httproute -A
kubectl describe httproute my-app

# Verify ALB was provisioned
kubectl get gateway my-gateway -o jsonpath='{.status.addresses[0].value}'

✅ Validation

  • ingress2gateway successfully converted Ingress to Gateway + HTTPRoute
  • GatewayClass aws-alb is accepted by AWS LBC
  • Gateway shows Programmed: True condition
  • HTTPRoute shows Accepted: True condition
  • ALB is provisioned and traffic routes correctly

Lab 4: Full Migration Scenario - Side-by-Side with Zero-Downtime Cutover

🎯 Objective

Simulate a real production migration: deploy ingress-nginx and AWS LBC side-by-side, run both controllers simultaneously, progressively shift traffic, and perform a zero-downtime cutover. Based on the F5 blog and AWS blog migration patterns.

⚡ Prerequisites

  • EKS cluster with node group
  • Helm 3.x installed
  • AWS LBC installed
  • A Route 53 hosted zone (for DNS-based traffic shifting)

1Deploy ingress-nginx (simulating legacy)

# Install ingress-nginx via Helm
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace \
  --set controller.service.type=LoadBalancer

# Wait for NLB to be provisioned
kubectl get svc -n ingress-nginx ingress-nginx-controller -w

2Deploy sample application with NGINX Ingress

# Deploy sample app
kubectl create deployment web-app --image=hashicorp/http-echo \
  --port=80 -- -text="Hello from web-app"
kubectl expose deployment web-app --port=80 --target-port=5678

# Create NGINX Ingress
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-nginx
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-app
            port:
              number: 80
EOF

# Get NGINX LB address
NGINX_LB=$(kubectl get svc -n ingress-nginx ingress-nginx-controller \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "NGINX LB: $NGINX_LB"

3Create AWS LBC Ingress (side-by-side)

# Create ALB Ingress pointing to the SAME backend
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-alb
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-app
            port:
              number: 80
EOF

# Get ALB address
ALB_DNS=$(kubectl get ingress web-app-alb \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo "ALB DNS: $ALB_DNS"

4Test both paths independently

# Test via NGINX (NLB)
curl -H "Host: app.example.com" http://$NGINX_LB/

# Test via AWS LBC (ALB)
curl -H "Host: app.example.com" http://$ALB_DNS/

# Both should return the same response

5Simulate progressive traffic shift (Route 53)

# In production, you would:
# 1. Create weighted Route 53 records:
#    - app.example.com -> NGINX_LB (weight: 90)
#    - app.example.com -> ALB_DNS  (weight: 10)
# 2. Monitor error rates and latency
# 3. Gradually shift: 90/10 -> 70/30 -> 50/50 -> 10/90 -> 0/100
# 4. Remove NGINX record when 100% on ALB

# For this lab, verify both endpoints work:
echo "NGINX: $(curl -s -H 'Host: app.example.com' http://$NGINX_LB/)"
echo "ALB:   $(curl -s -H 'Host: app.example.com' http://$ALB_DNS/)"

6Remove legacy ingress-nginx

# After full validation on ALB:
kubectl delete ingress web-app-nginx

# Uninstall ingress-nginx
helm uninstall ingress-nginx -n ingress-nginx
kubectl delete namespace ingress-nginx

7Cleanup

kubectl delete ingress web-app-alb
kubectl delete deployment web-app
kubectl delete service web-app

✅ Validation

  • Both NGINX and ALB Ingress resources coexist pointing to the same backend
  • Traffic works through both paths independently
  • Progressive traffic shift strategy is understood (Route 53 weighted records)
  • Legacy ingress-nginx is cleanly removed after cutover
  • No downtime during the entire migration process
