1. The NGINX Ingress Retirement - What Happened and Why

In November 2025, the Kubernetes SIG Network and Security Response Committee announced the retirement of the ingress-nginx project (kubernetes/ingress-nginx). As of March 2026, the repository is archived and read-only. No more releases, bug fixes, or security patches will be issued.

This impacts approximately 50% of cloud-native environments that depend on ingress-nginx. Organizations continuing to run it face escalating security risks from unpatched vulnerabilities, potential compliance violations (SOC 2, PCI-DSS, HIPAA), and operational risks from permanently unresolved issues.

⚠️ Critical Disambiguation (from field experience):
nginx/ingress (community controller) - DEAD, migrate ASAP
Ingress (Kubernetes API resource) - still valid, NOT going away
Gateway API - future direction, but NOT mandatory right now

Many customers confuse these: they read about nginx-ingress going away, see the Gateway API recommendation, and think they need to ditch Ingress entirely. They don't.

How to check if you're affected

🛠️ Try it yourself

# Run against each cluster to detect ingress-nginx
kubectl get pods --all-namespaces \
  --selector app.kubernetes.io/name=ingress-nginx

# Check the controller version
kubectl get deploy -n ingress-nginx \
  ingress-nginx-controller \
  -o jsonpath='{.spec.template.spec.containers[0].image}'

🔑 Key Concepts

  • ingress-nginx (kubernetes/ingress-nginx) - the community-maintained NGINX Ingress Controller, now retired
  • F5 NGINX Ingress Controller (nginxinc/kubernetes-ingress) - commercially supported by F5, still active
  • Kubernetes Ingress API - the standard API resource (networking.k8s.io/v1), still fully supported
  • Gateway API - next-gen Kubernetes networking API (CRDs), successor to Ingress API
  • Existing deployments continue to function after retirement but receive zero security patches
  • The retirement was driven by fundamental architectural limitations that made long-term maintenance impossible

2. Migration Options Overview - Decision Framework

There is no single "right" migration path. The best option depends on your architecture, scale, existing tooling, and timeline. Here's a decision framework based on real customer engagements:

OptionTargetBest ForLimitations
Option 1: AWS LBC via IngressAWS Load Balancer ControllerStandard EKS workloads, up to ~100 services/cluster, AWS-native integrations (ACM, WAF, Shield)100 Target Groups per ALB hard limit
Option 2: F5 NGINX ICF5 NGINX Ingress ControllerExisting F5 licensing, complex NGINX-specific configs, 200-300 services (avoids ALB TG limit)Commercial license required, in-cluster proxy overhead
Option 3: Envoy GatewayEnvoy-based Gateway API100+ services with path-based routing, single NLB/PrivateLink entry pointNewer ecosystem, less AWS-native integration
Option 4: Keep NGINX behind NLBTemporary bridgeShort-term while planning longer migrationNo security patches, growing risk over time

🔑 Decision Criteria

  • Service count per cluster: Under 100 services → AWS LBC is the simplest path. Over 100 → consider F5 NGINX IC or Envoy Gateway
  • AWS-native vs portable: AWS LBC gives you ACM, WAF, Shield, CloudWatch natively. Envoy Gateway is more portable across clouds
  • EKS Auto Mode: AWS LBC is natively included. Gateway API is NOT natively supported in Auto Mode yet (as of May 2026)
  • Timeline: Migrate ingress-nginx first (to AWS LBC via Ingress), then plan Gateway API adoption separately
  • PrivateLink architecture: If you have NLB + PrivateLink chains, the NLB stays - you're only replacing what's behind it

3. AWS LBC Architecture and Feature Comparison

The AWS Load Balancer Controller automates provisioning, configuration, and lifecycle management of both ALBs and NLBs as you deploy workloads in EKS. Unlike ingress-nginx (which runs as in-cluster pods acting as reverse proxy), AWS LBC provisions native AWS load balancers outside the cluster and routes traffic directly to pods via the VPC CNI.

Architecture Comparison

AspectNGINX Ingress (community)AWS Load Balancer Controller
Traffic flowAll traffic flows through NGINX pods (potential bottleneck)Routes directly to pods via AWS LB infrastructure
Load balancerRequires a LoadBalancer Service for external accessProvisions native ALB/NLB outside the cluster
TLS terminationKubernetes Secrets (in-cluster)AWS Certificate Manager (managed, auto-renewal)
SecuritySelf-managed, NGINX featuresNative WAF, Shield, Cognito/OIDC integration
ObservabilityNGINX metrics, custom dashboardsCloudWatch metrics, ALB access logs natively
ScalingManual pod scaling, linear cost increaseAutomatic, usage-based (LCU pricing)
MaintenanceSelf-managed (patching, upgrades, health)AWS-managed infrastructure
URI RewriteAnnotations + regexNative ALB URL rewrite (GA Oct 2025)

Key AWS LBC Features

As of v3.0, AWS LBC supports:

  • Ingress resources - provisions ALBs with path/host-based routing
  • Service type LoadBalancer - provisions NLBs
  • Gateway API (GA) - provisions ALBs and NLBs via Gateway/HTTPRoute/TCPRoute CRDs
  • IngressGroup - share a single ALB across multiple Ingress resources
  • Target type: ip - direct pod routing (no NodePort hop), recommended for performance
  • URL rewrite - native regex-based URI rewriting on ALB (no NGINX needed)
  • Certificate discovery - auto-discovers ACM certificates by hostname

🔑 Key Concepts

  • ALB (Application Load Balancer): Layer 7 (HTTP/HTTPS) - path/host routing, WAF, auth, URL rewrite
  • NLB (Network Load Balancer): Layer 4 (TCP/UDP) - high throughput, low latency, PrivateLink compatible
  • Target type ip: Routes directly to pod IPs via VPC CNI - eliminates NodePort hop, better performance
  • IngressGroup: Annotation that groups multiple Ingress resources behind a single ALB (cost optimization)
  • 100 Target Groups per ALB: Hard limit, not adjustable. Key constraint for high-density clusters
  • LCU pricing: Pay per Load Balancer Capacity Unit based on actual connections/requests/data processed

4. Migrating Ingress Resources - URI Rewrite, TLS, Annotations

The most common migration path for AWS customers: replace ingress-nginx with AWS LBC while keeping standard Kubernetes Ingress resources. The key is mapping NGINX annotations to AWS LBC annotations.

Example 1: URI Rewrite

Route traffic from rewrite.bar.com/something/* to backend at /*, removing the /something prefix.

NGINX Ingress (before)

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
  - host: rewrite.bar.com
    http:
      paths:
      - path: /something(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: http-svc
            port:
              number: 80

AWS LBC (after)

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/transforms.http-svc: |
      [
        {
          "type": "url-rewrite",
          "urlRewriteConfig": {
            "rewrites": [
              {
                "regex": "^\\/something\\/(.*)$",
                "replace": "/$1"
              }
            ]
          }
        }
      ]
spec:
  ingressClassName: alb
  rules:
  - host: rewrite.bar.com
    http:
      paths:
      - path: /something
        pathType: Prefix
        backend:
          service:
            name: http-svc
            port:
              number: 80
Gotchas: The transforms.http-svc annotation name MUST match your service name. Forward slashes must be escaped as \\/ in JSON regex. Test regex patterns carefully - ALB regex syntax may differ slightly from NGINX.

Example 2: Adding TLS Termination

# AWS LBC with TLS (add these annotations)
alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:REGION:ACCOUNT:certificate/CERT-ID
alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
alb.ingress.kubernetes.io/ssl-redirect: '443'
alb.ingress.kubernetes.io/ssl-policy: ELBSecurityPolicy-TLS-1-2-2017-01

# Or use certificate discovery (no ARN needed)
alb.ingress.kubernetes.io/certificate-discovery: "true"

Common Annotation Mapping

NGINX AnnotationAWS LBC Equivalent
nginx.ingress.kubernetes.io/rewrite-targetalb.ingress.kubernetes.io/transforms.SVC_NAME (url-rewrite)
nginx.ingress.kubernetes.io/ssl-redirectalb.ingress.kubernetes.io/ssl-redirect: '443'
nginx.ingress.kubernetes.io/proxy-read-timeoutALB idle timeout (default 60s, configurable)
nginx.ingress.kubernetes.io/affinity: cookieALB sticky sessions via target group attributes
nginx.ingress.kubernetes.io/cors-*ALB response headers (via Lambda@Edge or transforms)
nginx.ingress.kubernetes.io/whitelist-source-rangeSecurity Groups on ALB

🔑 Key Concepts

  • ingressClassName: Change from nginx to alb
  • Certificate management: Moves from K8s Secrets to ACM (auto-renewal, no in-cluster secrets)
  • URL rewrite: Native ALB feature since Oct 2025 - no more NGINX regex hacks
  • IngressGroup: Use alb.ingress.kubernetes.io/group.name to share one ALB across multiple Ingress resources
  • Target type ip: Always use alb.ingress.kubernetes.io/target-type: ip for direct pod routing

Migration Checklist

✅ Pre-Migration

  • Audit existing NGINX Ingress configurations and annotations
  • Request/import certificates in AWS Certificate Manager
  • Plan IngressGroup strategy for shared ALBs
  • Install AWS LBC in the cluster

✅ During Migration

  • Convert NGINX annotations to AWS LBC annotations
  • Update ingressClassName from nginx to alb
  • Test URI rewrite patterns thoroughly
  • Monitor ALB metrics and logs

✅ Post-Migration

  • Remove NGINX Ingress Controller after validation
  • Clean up unused K8s Secrets (certificates)
  • Set up ALB access logging
  • Configure WAF rules if needed

5. Kubernetes Gateway API Fundamentals

Gateway API is the next-generation Kubernetes networking API, designed by SIG-Network to address the fundamental limitations of the Ingress API. It provides a role-oriented, expressive, and extensible model for managing traffic routing.

Why Gateway API?

The Ingress API has several design limitations that Gateway API solves:

  • Vendor-specific annotations: Ingress relies on controller-specific annotations for anything beyond basic routing. Gateway API uses typed CRDs with schema validation
  • No role separation: Ingress combines infrastructure and application concerns. Gateway API splits them into GatewayClass (platform), Gateway (infra ops), and Routes (app devs)
  • Limited protocol support: Ingress only supports HTTP/HTTPS. Gateway API natively supports HTTP, HTTPS, gRPC, TCP, UDP, TLS
  • No cross-namespace routing: Ingress is namespace-scoped. Gateway API supports cross-namespace routing with explicit grants

Core Resources

ResourceOwnerPurpose
GatewayClassPlatform teamDefines the controller implementation (like StorageClass for storage)
GatewayInfra/cluster opsInstantiates the load balancer, defines listeners (ports, protocols, TLS)
HTTPRouteApp developersDefines routing rules: path matching, header matching, traffic splitting
GRPCRouteApp developersgRPC-specific routing rules
TCPRoute / UDPRoute / TLSRouteApp developersL4 routing for non-HTTP protocols

Ingress vs Gateway API - Side by Side

# Ingress (old way)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
---
# Gateway API (new way)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
spec:
  parentRefs:
  - name: my-gateway
  hostnames:
  - app.example.com
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: api-svc
      port: 80

ingress2gateway Tool

SIG-Network shipped ingress2gateway v1.0 in March 2026 - a migration tool that reads existing Ingress resources and converts them to Gateway + HTTPRoute resources. It supports ingress-nginx annotations and provides warnings for untranslatable configurations.

🛠️ Try it yourself

# Install ingress2gateway
go install github.com/kubernetes-sigs/ingress2gateway@latest

# Convert existing Ingress resources
ingress2gateway print --providers ingress-nginx \
  --input-file my-ingress.yaml

# Or convert from live cluster
kubectl get ingress -A -o yaml | ingress2gateway print --providers ingress-nginx

🔑 Key Concepts

  • Role-oriented design: Platform team manages GatewayClass, infra ops manages Gateway, app devs manage Routes
  • Type-safe CRDs: Schema validation catches errors at apply time, not at runtime
  • Portable: Same HTTPRoute works across different implementations (AWS LBC, Envoy Gateway, Cilium, Istio)
  • Conformance profiles: Implementations declare which features they support via conformance reports
  • ingress2gateway: Official SIG-Network tool for automated Ingress-to-Gateway conversion
  • Side-by-side deployment: You can run Gateway API alongside existing Ingress - they get different IPs

6. AWS LBC v3 + Gateway API on EKS

AWS Load Balancer Controller v3.0 added GA support for Kubernetes Gateway API. This means you can use the same controller for both Ingress resources (ALB) and Gateway API resources (ALB + NLB), providing a smooth migration path.

How it works on EKS

AWS LBC reconciles Gateway API objects and maps them to AWS load balancers:

  • L7 routes (HTTPRoute, GRPCRoute) → provisions an ALB
  • L4 routes (TCPRoute, UDPRoute, TLSRoute) → provisions an NLB
  • Automatic TLS certificate discovery for both L4 and L7
  • Eliminates annotation-based config in favor of typed CRDs

Example: HTTPRoute with AWS LBC

# GatewayClass (platform team)
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: aws-alb
spec:
  controllerName: gateway.k8s.aws/alb
---
# Gateway (infra ops)
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
spec:
  gatewayClassName: aws-alb
  listeners:
  - name: http
    port: 80
    protocol: HTTP
  - name: https
    port: 443
    protocol: HTTPS
    tls:
      mode: Terminate
      certificateRefs:
      - name: my-cert  # auto-discovered from ACM
---
# HTTPRoute (app developer)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
spec:
  parentRefs:
  - name: my-gateway
  hostnames:
  - app.example.com
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    backendRefs:
    - name: api-svc
      port: 80

AWS LBC + VPC Lattice: Complementary Use Cases

Use CaseControllerData Plane
Internet ingress, WAF, ACM, ALB featuresAWS LBCALB / NLB
Cross-cluster communicationVPC Lattice Gateway API ControllerVPC Lattice
Cross-VPC / cross-accountVPC Lattice Gateway API ControllerVPC Lattice
Service-to-service authVPC Lattice Gateway API ControllerVPC Lattice

Both controllers can run simultaneously using the same Gateway API specification - just different GatewayClass names.

🔑 Key Concepts

  • controllerName: gateway.k8s.aws/alb for AWS LBC, application-networking.k8s.aws/gateway-api-controller for VPC Lattice
  • ListenerRuleConfiguration: AWS LBC CRD for advanced ALB listener rules (custom routing beyond HTTPRoute)
  • Recommended migration path: Ingress NGINX → AWS LBC (Ingress) → AWS LBC (Gateway API)
  • EKS Auto Mode: Supports AWS LBC natively for Ingress. Gateway API support in Auto Mode is not yet available
  • QUIC/HTTP3: AWS LBC supports QUIC protocol on NLBs via Gateway API

7. Real-World Migration Scenarios and Gotchas

Based on real customer engagements and field experience, here are the patterns, pitfalls, and production-proven strategies for NGINX Ingress migration.

Scenario A: Standard EKS Cluster (<100 services)

Pattern: NGINX Ingress → AWS LBC via Ingress resources

  • Install AWS LBC alongside existing ingress-nginx
  • Create new Ingress resources with ingressClassName: alb
  • Test with non-production workloads first
  • Gradually shift traffic via DNS (weighted routing in Route 53)
  • Remove ingress-nginx after full validation

Scenario B: High-Density Cluster (100+ services, PrivateLink)

Pattern: NGINX Ingress → Envoy Gateway (in-cluster L7 proxy)

Real case (large-scale platform): 200+ apps per cluster, each in its own namespace with path-based routing behind PrivateLink. ALB was validated end-to-end (URL rewrite, TLS, IngressGroup, PrivateLink chain) but hit the 100 Target Group limit as a production blocker. Envoy Gateway was the recommended solution. 
# Architecture: NLB + PrivateLink stays, replace what's behind it
NLB (PrivateLink) → Envoy Gateway pods (in-cluster L7) → per-app pods

Scenario C: F5 NGINX Migration (complex configs)

Pattern: Community NGINX → F5 NGINX Ingress Controller

F5 offers two migration paths:

  1. Via NGINX Ingress Resources (VirtualServer, VirtualServerRoute CRDs) - optimal for production, broader capabilities
  2. Via standard Kubernetes Ingress Resource - simpler, keeps all config in Ingress objects

Technical Gotchas (from field)

⚠️ Watch Out For

  • Annotation aws-load-balancer-type: external: Changing this may trigger NLB recreation depending on which controller manages the Service (in-tree vs AWS LBC). Validate which controller is active BEFORE changing
  • Finalizer removal: Sensitive operation during migration. Always check kubectl get svc NAME -o jsonpath='{.metadata.finalizers}' before removing
  • ALB 100 TG limit: Hard limit, not adjustable. If you have 100+ services with path-based routing, ALB won't work. Plan for Envoy Gateway or F5 NGINX
  • VPC Lattice limits: Default 10 rules/listener, 10 TGs/service - also doesn't fit high-density scenarios
  • Pod Readiness Gates: Enable for AWS LBC to avoid 5xx during deployments (pods registered before ready)
  • Deregistration delay: Reduce from 300s to 30-60s for stateless microservices
  • Rollback strategy: Keep old NodeGroup and old TargetGroup in the NLB listener until 100% traffic is validated. Rollback = revert listener weight

Zero-Downtime Migration Strategy

  1. Side-by-side deployment: Install new controller alongside old one (different external IPs)
  2. Progressive validation: Shift dev traffic first, then staging, then production
  3. DNS cutover: Use Route 53 weighted routing to gradually shift traffic
  4. Shared-IP strategy: If both controllers can share the same LB IP, DNS cutover is seamless
  5. Monitoring: Watch error rates, latency, and connection counts during transition
