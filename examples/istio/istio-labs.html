Lab 3: Network Resiliency

🎯 Objective

Configure circuit breaker, retries, timeouts, and fault injection. Test resiliency by injecting a 7-second delay on the ratings service.

1Apply destination rules

kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.24/samples/bookinfo/networking/destination-rule-all.yaml

2Inject a 7s delay on ratings (fault injection)

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: ratings
spec:
  hosts:
  - ratings
  http:
  - fault:
      delay:
        percentage:
          value: 100.0
        fixedDelay: 7s
    route:
    - destination:
        host: ratings
        subset: v1
EOF

# Verify: productpage takes ~7s to load (reviews waits for ratings)
# The reviews service has a 10s timeout, so it still works but slowly

3Add a timeout on reviews (2.5s)

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
  - reviews
  http:
  - route:
    - destination:
        host: reviews
        subset: v2
    timeout: 2.5s
EOF

# Verify: productpage now returns quickly (~2.5s)
# Reviews section shows "Sorry, product reviews are currently unavailable"
# because the 2.5s timeout fires before the 7s delay completes

4Configure circuit breaker

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: ratings-cb
spec:
  host: ratings
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 1
      http:
        http1MaxPendingRequests: 1
        maxRequestsPerConnection: 1
    outlierDetection:
      consecutive5xxErrors: 1
      interval: 5s
      baseEjectionTime: 30s
      maxEjectionPercent: 100
EOF

# Test with fortio (load generator)
kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.24/samples/httpbin/sample-client/fortio-deploy.yaml
FORTIO_POD=$(kubectl get pods -l app=fortio -o jsonpath='{.items[0].metadata.name}')

# Send 20 concurrent requests
kubectl exec $FORTIO_POD -c fortio -- fortio load -c 3 -qps 0 -n 20 -loglevel Warning http://ratings:9080/ratings/0

# Look for "Code 503" responses - those are circuit breaker trips

5Cleanup

kubectl delete virtualservice ratings reviews
kubectl delete destinationrule ratings-cb

✅ Validation

  • 7s delay: productpage loads slowly (~7s) with ratings delay injected
  • 2.5s timeout: productpage returns quickly, reviews shows "unavailable"
  • Circuit breaker: fortio output shows mix of 200 and 503 responses

Lab 4: mTLS + AuthorizationPolicy

🎯 Objective

Enable STRICT mTLS mesh-wide, create a deny-all authorization policy, then add explicit ALLOW rules for BookInfo service communication.

1Check current mTLS status

# Check mTLS status for all services
istioctl authn tls-check | head -20

# Default mode is PERMISSIVE - accepts both mTLS and plaintext

2Enable STRICT mTLS mesh-wide

cat <<'EOF' | kubectl apply -f -
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
EOF

# Verify: all connections now require mTLS
istioctl authn tls-check | head -20

3Create deny-all policy

cat <<'EOF' | kubectl apply -f -
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: deny-all
  namespace: default
spec:
  {}
EOF

# Verify: productpage should return RBAC: access denied
curl -s http://$INGRESS_HOST/productpage | head -5

4Add ALLOW rules for BookInfo

# Allow ingress gateway to reach productpage
cat <<'EOF' | kubectl apply -f -
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-productpage
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/istio-system/sa/istio-ingressgateway-service-account"]
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-reviews
  namespace: default
spec:
  selector:
    matchLabels:
      app: reviews
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/bookinfo-productpage"]
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-ratings
  namespace: default
spec:
  selector:
    matchLabels:
      app: ratings
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/bookinfo-reviews"]
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-details
  namespace: default
spec:
  selector:
    matchLabels:
      app: details
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/bookinfo-productpage"]
EOF

# Verify: productpage works again with full BookInfo chain

5Cleanup

kubectl delete authorizationpolicy deny-all allow-productpage allow-reviews allow-ratings allow-details
kubectl delete peerauthentication default -n istio-system

✅ Validation

  • STRICT mTLS: istioctl authn tls-check shows all connections as mTLS
  • deny-all: productpage returns "RBAC: access denied"
  • ALLOW rules: productpage works with full BookInfo chain (details + reviews + ratings)
  • Unauthorized paths are still denied (e.g., direct access to reviews from outside)

Lab 8: Troubleshooting Scenarios

🎯 Objective

Diagnose and fix 4 common Istio misconfigurations. Each scenario creates its own broken environment (dedicated namespace), presents symptoms, requires investigation, and has a specific fix. All scenarios run on the same cluster provisioned in Lab 0.

⚡ Prerequisites

  • Lab 0 completed - EKS cluster with Istio running
  • Lab 1 completed - BookInfo deployed in default namespace with sidecars (2/2)
  • Lab 6 completed - Ambient mode installed (required for Scenario 4 only)
  • kubectl context pointing to the Lab 0 cluster: kubectl config current-context

🎯 How This Lab Works

Each scenario below creates its own isolated namespace (broken-1, broken-2, etc.) with intentional misconfigurations. You investigate the symptoms, find the root cause, and apply the fix. The setup commands at the start of each scenario create the broken state - run them first, then try to diagnose before looking at the fix.

All scenarios use the cluster from Lab 0. No additional infrastructure needed.

Scenario 1: Sidecar Injection Not Working

Symptoms: Pods show 1/1 instead of 2/2. No mTLS, no traffic management.

# Setup: create namespace without injection label
kubectl create namespace broken-1
kubectl apply -n broken-1 -f https://raw.githubusercontent.com/istio/istio/release-1.24/samples/bookinfo/platform/kube/bookinfo.yaml

# Investigation
kubectl get namespace broken-1 --show-labels
kubectl get pods -n broken-1  # Shows 1/1
istioctl analyze -n broken-1  # Should warn about missing injection

# Fix
kubectl label namespace broken-1 istio-injection=enabled
kubectl rollout restart deployment -n broken-1

# Validate
kubectl get pods -n broken-1  # Should show 2/2

Scenario 2: mTLS STRICT but Missing PeerAuthentication

Symptoms: Services in a non-mesh namespace cannot reach mesh services. Connection refused errors.

# Setup: enable STRICT mTLS, deploy a client outside the mesh
kubectl create namespace broken-2
# (do NOT label for injection)
kubectl run curl-client -n broken-2 --image=curlimages/curl --command -- sleep 3600

# Apply STRICT mTLS
cat <<'EOF' | kubectl apply -f -
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: strict-test
  namespace: default
spec:
  mtls:
    mode: STRICT
EOF

# Investigation
kubectl exec -n broken-2 curl-client -- curl -s http://productpage.default:9080/productpage
# Result: connection reset / refused (non-mesh client can't do mTLS)

# Fix option 1: Add the client to the mesh
kubectl label namespace broken-2 istio-injection=enabled
kubectl delete pod curl-client -n broken-2
kubectl run curl-client -n broken-2 --image=curlimages/curl --command -- sleep 3600

# Fix option 2: Set PERMISSIVE for the specific service
cat <<'EOF' | kubectl apply -f -
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: productpage-permissive
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  mtls:
    mode: PERMISSIVE
EOF

# Validate
kubectl exec -n broken-2 curl-client -- curl -s http://productpage.default:9080/productpage | head -5

Scenario 3: Circuit Breaker Too Aggressive

Symptoms: All requests to a service fail with 503. Service pods are healthy.

# Setup: apply overly aggressive circuit breaker
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: ratings-aggressive-cb
spec:
  host: ratings
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 1
      http:
        http1MaxPendingRequests: 1
        maxRequestsPerConnection: 1
    outlierDetection:
      consecutive5xxErrors: 1
      interval: 1s
      baseEjectionTime: 300s
      maxEjectionPercent: 100
EOF

# Investigation
kubectl get destinationrule ratings-aggressive-cb -o yaml
# Notice: maxEjectionPercent=100 + consecutive5xxErrors=1 + baseEjectionTime=300s
# A single error ejects ALL endpoints for 5 minutes

istioctl proxy-config cluster productpage-v1-xxx | grep ratings
# Check for "outlier_detection" stats

# Fix: relax the circuit breaker
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: ratings-aggressive-cb
spec:
  host: ratings
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 100
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
EOF

# Validate: requests succeed again

Scenario 4: Waypoint Proxy OOMKilled

Symptoms: Waypoint proxy pod keeps restarting. L7 features intermittently fail in ambient namespace.

Requires: Lab 6 completed (ambient mode installed). If you skipped Lab 6, run the ambient install first.

# Setup: create an ambient namespace with a waypoint that has insufficient resources
kubectl create namespace broken-4
kubectl label namespace broken-4 istio.io/dataplane-mode=ambient

# Deploy BookInfo in ambient namespace
kubectl apply -n broken-4 -f https://raw.githubusercontent.com/istio/istio/release-1.24/samples/bookinfo/platform/kube/bookinfo.yaml
kubectl wait --for=condition=ready pod -l app=productpage -n broken-4 --timeout=60s

# Deploy waypoint with insufficient resources
cat <<'EOF' | kubectl apply -f -
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: bookinfo-waypoint
  namespace: broken-4
  labels:
    istio.io/waypoint-for: service
spec:
  gatewayClassName: istio-waypoint
  listeners:
  - name: mesh
    port: 15008
    protocol: HBONE
EOF

# Investigation
kubectl get pods -n broken-4 -l gateway.networking.k8s.io/gateway-name
kubectl describe pod -n broken-4 -l gateway.networking.k8s.io/gateway-name
# Look for: OOMKilled, Last State: Terminated (reason: OOMKilled)

kubectl top pod -n broken-4 -l gateway.networking.k8s.io/gateway-name

# Fix: increase waypoint resource limits
# Edit the waypoint deployment or use Helm values to increase memory
kubectl patch deployment bookinfo-waypoint -n broken-4 --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/memory","value":"512Mi"}]'

# Validate
kubectl get pods -n broken-4 -l gateway.networking.k8s.io/gateway-name
# Pod should be Running without restarts

Cleanup (all troubleshooting scenarios)

# Remove all troubleshooting namespaces
kubectl delete namespace broken-1 broken-2 broken-4

# Remove the aggressive circuit breaker from default namespace
