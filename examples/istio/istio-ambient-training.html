7. Ambient Mode Architecture

Ambient mode is Istio's sidecar-less data plane, introduced as a major architectural evolution. Instead of injecting an Envoy sidecar into every pod, ambient mode splits mesh functionality into two layers: a per-node ztunnel for L4 and optional per-namespace waypoint proxies for L7.

ztunnel - Per-Node L4 Proxy

ztunnel (zero-trust tunnel) runs as a DaemonSet - one instance per node. It handles:

  • mTLS encryption: All pod-to-pod traffic is encrypted transparently, just like sidecar mode
  • L4 authorization: Enforces AuthorizationPolicy rules at the TCP level (source/destination identity, port)
  • Telemetry: Collects L4 metrics (TCP connections, bytes transferred)

ztunnel uses the HBONE protocol (HTTP-based overlay network encapsulation) to tunnel traffic between nodes. It intercepts traffic at the node level using eBPF or iptables (via Istio CNI), eliminating the need for per-pod sidecars.

Waypoint Proxies - Per-Namespace L7

Waypoint proxies are Envoy instances deployed per-namespace (or per-service) that handle L7 features:

  • HTTP routing (VirtualService rules, header-based routing)
  • L7 authorization (path-based, method-based AuthorizationPolicy)
  • Traffic management (retries, timeouts, fault injection, traffic splitting)
  • L7 telemetry (HTTP metrics, distributed tracing)

Waypoint proxies are optional - you only deploy them for namespaces that need L7 features. This is the key cost optimization: most services only need mTLS and L4 auth (handled by ztunnel), and only a subset needs full L7 capabilities.

# Deploy a waypoint proxy for a namespace
istioctl waypoint apply --namespace bookinfo

# Or via Kubernetes Gateway API
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: bookinfo-waypoint
  namespace: bookinfo
  labels:
    istio.io/waypoint-for: service
spec:
  gatewayClassName: istio-waypoint
  listeners:
  - name: mesh
    port: 15008
    protocol: HBONE

L4/L7 Split - Why It Matters

The L4/L7 split is the fundamental innovation of ambient mode:

  • Cost: Sidecars consume CPU/memory per pod. ztunnel is per-node (shared). For a node with 30 pods, you go from 30 Envoy instances to 1 ztunnel + 0-1 waypoint proxies.
  • Performance: ztunnel is a purpose-built Rust proxy optimized for L4. Lower latency than full Envoy for mTLS-only workloads.
  • Operations: No sidecar injection means no pod restarts for mesh upgrades. ztunnel DaemonSet can be upgraded independently.

Istio CNI in Ambient Mode

The Istio CNI plugin is required for ambient mode (not optional like in sidecar mode). It configures traffic redirection at the node level to route pod traffic through ztunnel.

🔑 Key Concepts

  • ztunnel: Per-node L4 proxy (DaemonSet). Handles mTLS, L4 auth, L4 telemetry. Written in Rust
  • Waypoint proxy: Per-namespace Envoy for L7 features. Optional - deploy only where needed
  • HBONE: HTTP-based overlay network encapsulation. Protocol used by ztunnel for inter-node traffic
  • L4/L7 split: ztunnel handles L4 (mTLS, TCP auth), waypoint handles L7 (HTTP routing, tracing)
  • Istio CNI required: Ambient mode requires the CNI plugin for traffic interception at node level
  • No sidecar injection: Namespace label istio.io/dataplane-mode=ambient instead of istio-injection=enabled

8. Sidecar vs Ambient - Decision Framework

Sidecar and ambient modes can coexist in the same mesh. The choice depends on workload requirements, cost sensitivity, and operational maturity.

Full Comparison

When to Use Sidecar

  • Multi-cluster deployments requiring mature cross-cluster communication
  • VM workloads that need mesh integration
  • Full L7 features needed on every service (not just a subset)
  • Wasm plugin extensibility on every workload
  • Production environments requiring battle-tested stability

When to Use Ambient

  • Zero-trust first: you primarily need mTLS and L4 authorization across all services
  • Selective L7: only a subset of services need HTTP routing, tracing, or L7 auth
  • Cost optimization: large clusters where sidecar overhead is significant
  • Operational simplicity: avoid sidecar injection complexity and pod restart requirements
  • New mesh deployments without existing sidecar investment

Migration Path: Sidecar to Ambient

Sidecar and ambient modes coexist in the same mesh. Migration is per-namespace:

  1. Remove istio-injection=enabled label from namespace
  2. Add istio.io/dataplane-mode=ambient label
  3. Restart pods to remove sidecars (they join the mesh via ztunnel automatically)
  4. Deploy waypoint proxy if L7 features are needed
  5. Validate connectivity and policies

🔑 Key Concepts

  • Coexistence: Sidecar and ambient namespaces can communicate within the same mesh
  • Sidecar strengths: Multi-cluster maturity, VM support, full L7 everywhere, Wasm extensibility
  • Ambient strengths: Lower resource cost, no pod restarts for upgrades, selective L7, simpler operations
  • Migration: Per-namespace, non-disruptive. Change labels, restart pods, optionally add waypoint
  • Decision driver: If >80% of services only need mTLS + L4 auth, ambient is likely the better choice

9. Istio on EKS - AWS-Specific Considerations

Running Istio on EKS requires understanding how Istio interacts with AWS-specific networking components: VPC CNI, ALB/NLB, Karpenter, and multi-AZ topologies.

VPC CNI Compatibility

The Amazon VPC CNI plugin assigns real VPC IP addresses to pods. Istio works well with VPC CNI because pod IPs are routable within the VPC. Key considerations:

  • VPC CNI's ENABLE_PREFIX_DELEGATION works with Istio (more IPs per node)
  • Security groups for pods (SGP) work with Istio sidecars but require careful configuration
  • Network Policy enforcement: VPC CNI network policy and Istio AuthorizationPolicy are complementary (VPC CNI at L3/L4, Istio at L4/L7)

Istio CNI Plugin on EKS

The Istio CNI plugin is recommended on EKS to avoid requiring NET_ADMIN capability in init containers. This is especially important when using Pod Security Standards (restricted profile) or when running on Fargate (where init containers with elevated privileges are restricted).

ALB Integration with Istio Gateway

Two common patterns for exposing Istio services externally on EKS:

  • NLB + Istio IngressGateway: AWS NLB fronts the Istio ingress gateway (Envoy). TLS termination at Istio level. Most common pattern.
  • ALB + Istio: AWS ALB terminates TLS and routes to Istio services. Requires careful configuration to preserve headers and client IP.

Karpenter Considerations

  • Node sizing for sidecars: Each sidecar adds ~128MB memory + 100m CPU. Factor this into Karpenter NodePool resource limits.
  • ztunnel DaemonSet: In ambient mode, ztunnel runs on every node. Karpenter must account for DaemonSet overhead when right-sizing nodes.
  • Disruption budgets: Configure Karpenter's consolidationPolicy to respect Istio's PodDisruptionBudgets during node consolidation.

Locality-Aware Routing (Multi-AZ Cost Optimization)

Istio supports locality-aware routing to keep traffic within the same AZ, reducing cross-AZ data transfer costs. Configure via DestinationRule with localityLbSetting. On EKS, this maps to AWS Availability Zones automatically via node topology labels.

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      localityLbSetting:
        enabled: true
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s

10. Ambient Mode on EKS Auto Mode

EKS Auto Mode simplifies cluster operations by managing node groups, scaling, and add-ons automatically. However, running Istio (especially ambient mode) on EKS Auto Mode has specific considerations and limitations as of May 2026.

Current Status (May 2026)

  • Sidecar mode: Works on EKS Auto Mode with some caveats (Istio CNI plugin must be configured carefully alongside Auto Mode's managed CNI)
  • Ambient mode: Limited support. ztunnel DaemonSet requires node-level access that Auto Mode restricts. Solo.io has been working with AWS to address this.
  • Key limitation: EKS Auto Mode manages the CNI and node configuration. Custom DaemonSets (like ztunnel) that modify node networking may conflict with Auto Mode's managed components.

Solo.io Partnership with AWS

Solo.io (the company behind Gloo Mesh and major Istio contributors) has partnered with AWS to accelerate Istio support on EKS Auto Mode. Their Gloo Mesh Enterprise product provides a managed Istio experience that integrates with EKS Auto Mode's constraints.

What Works and What Doesn't

⚠️ Evolving Landscape: EKS Auto Mode + Istio ambient is actively being developed. Check the latest Istio and EKS release notes before planning production deployments. For production ambient on EKS, consider standard managed node groups until Auto Mode support matures.

🔑 Key Concepts

  • EKS Auto Mode: Managed nodes, scaling, and add-ons. Restricts node-level customization
  • Sidecar on Auto Mode: Works. Standard webhook injection, no node-level changes needed
  • Ambient on Auto Mode: Limited. ztunnel DaemonSet conflicts with managed node networking
  • Solo.io/Gloo Mesh: Managed Istio product with EKS Auto Mode integration
  • Recommendation: For ambient mode, use standard EKS managed node groups until Auto Mode support matures

11. Advanced Patterns

Production Istio deployments on EKS often require multi-cluster topologies, cross-cluster identity federation, and AZ-aware resilience strategies.

Multi-Cluster Multi-Primary

In a multi-primary topology, each EKS cluster runs its own Istiod control plane. Clusters share a common trust domain and root CA, enabling cross-cluster mTLS. Services are discovered across clusters via Istio's remote secret mechanism.

Key considerations for EKS:

  • Clusters can be in different VPCs (requires VPC peering or Transit Gateway)
  • Each cluster needs its own Istiod but shares the root CA certificate
  • Cross-cluster traffic flows through the east-west gateway (dedicated Envoy)
  • The aws-samples/istio-on-eks repo has a complete multi-primary pattern

SPIFFE/SPIRE Federation

For environments requiring identity federation beyond Istio's built-in CA, SPIRE (the SPIFFE Runtime Environment) can replace Istiod's Citadel as the certificate authority. This enables:

  • Cross-mesh identity federation (Istio mesh A trusts identities from mesh B)
  • Integration with non-mesh workloads (VMs, serverless) using SPIFFE SVIDs
  • Compliance with strict PKI requirements (custom CA hierarchies, HSM-backed keys)

AZ Resilience with EKS Zonal Shift + Istio

When an AZ experiences degradation, EKS Zonal Shift can evacuate traffic from the impaired AZ. Combined with Istio's locality-aware routing and outlier detection, this provides end-to-end AZ resilience:

  • EKS Zonal Shift handles the infrastructure layer (moves pods and load balancer targets)
  • Istio's outlier detection ejects unhealthy endpoints in the impaired AZ
  • Locality-aware routing redirects traffic to healthy AZs
  • Combined, they provide faster recovery than either mechanism alone

🔑 Key Concepts

  • Multi-primary: Each cluster has its own Istiod. Shared root CA enables cross-cluster mTLS
  • East-west gateway: Dedicated Envoy for cross-cluster traffic. Required for multi-network topologies
  • SPIFFE/SPIRE: External identity provider replacing Istiod's CA. Enables cross-mesh federation
  • EKS Zonal Shift + Istio: Infrastructure-level AZ evacuation + mesh-level traffic steering = end-to-end resilience
  • IPv6 integration: Istio supports IPv6 EKS clusters for environments scaling beyond IPv4 address space
