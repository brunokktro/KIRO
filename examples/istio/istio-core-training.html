1. Service Mesh Concepts

A service mesh is a dedicated infrastructure layer that handles service-to-service communication within a microservices architecture. Instead of embedding networking logic (retries, timeouts, mTLS, observability) into each application, the mesh provides these capabilities transparently through proxies deployed alongside each workload.

Why Service Meshes Exist

As organizations move from monoliths to microservices, the number of network hops between services explodes. Each hop introduces failure modes: latency spikes, partial failures, security gaps. Libraries like Netflix Hystrix tried to solve this at the application layer, but that approach requires every team to adopt the same library, in the same language, with consistent configuration. A service mesh decouples networking concerns from application code entirely.

Data Plane vs Control Plane

Every service mesh has two fundamental components:

  • Data Plane: The set of proxies (sidecars) that intercept all network traffic between services. In Istio, this is Envoy Proxy.
  • Control Plane: The management layer that configures and coordinates the data plane proxies. In Istio, this is Istiod. It pushes configuration via xDS APIs.

The Sidecar Pattern

In sidecar mode, Istio injects an Envoy proxy container into every pod. An init container (or the Istio CNI plugin) configures iptables rules to redirect all inbound and outbound traffic through the sidecar. The application is completely unaware of the mesh.

🔑 Key Concepts

  • Service Mesh: Infrastructure layer for service-to-service communication - handles mTLS, routing, observability without app changes
  • Envoy Proxy: High-performance L4/L7 proxy, the universal data plane for Istio
  • Sidecar Pattern: Envoy runs as a container alongside the app in the same pod, intercepting all traffic via iptables
  • xDS APIs: The protocol Istiod uses to push configuration to Envoy sidecars (LDS, RDS, CDS, EDS, SDS)
  • mTLS by default: All service-to-service traffic is encrypted and mutually authenticated without app changes
  • Traffic interception: iptables rules (or Istio CNI) redirect pod traffic through the sidecar transparently

2. Istio Architecture

Istio's architecture has evolved significantly. Early versions had separate control plane components (Pilot, Citadel, Galley, Mixer). Since Istio 1.5, these were consolidated into a single binary: Istiod.

Istiod - The Unified Control Plane

  • Pilot: Service discovery and traffic management. Converts routing rules into Envoy-specific configuration via xDS.
  • Citadel: Certificate authority. Issues SPIFFE-based X.509 certificates to all workloads for mTLS.
  • Galley: Configuration validation and distribution.

Sidecar Injection

  • Automatic: Label namespace with istio-injection=enabled. Mutating webhook adds sidecar to every new pod.
  • Manual: Use istioctl kube-inject to modify YAML before applying.

Istio CNI Plugin

Eliminates the init container with NET_ADMIN/NET_RAW capabilities by configuring traffic redirection at the CNI level. Important for Pod Security Standards restricted profile and platforms like EKS with strict security policies.

🔑 Key Concepts

  • Istiod: Single control plane binary (Pilot + Citadel + Galley). Runs as Deployment in istio-system
  • Automatic sidecar injection: Namespace label istio-injection=enabled triggers mutating webhook
  • Istio CNI Plugin: Eliminates init container with NET_ADMIN. Required for PSS restricted profile
  • SPIFFE identity: Each workload gets spiffe://cluster.local/ns/{namespace}/sa/{service-account}

3. Traffic Management

Traffic management is Istio's core value proposition. It decouples traffic routing from deployment topology, enabling canary deployments, A/B testing, traffic mirroring, and header-based routing without modifying application code.

VirtualService - Routing Rules

Defines how requests are routed. Supports match conditions based on URI, headers, query parameters, source labels. Multiple match rules evaluated in order - first match wins.

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
  - reviews
  http:
  - match:
    - headers:
        end-user:
          exact: jason
    route:
    - destination:
        host: reviews
        subset: v2
  - route:
    - destination:
        host: reviews
        subset: v1

DestinationRule - Subsets and Load Balancing

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  trafficPolicy:
    loadBalancer:
      simple: ROUND_ROBIN
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
  - name: v3
    labels:
      version: v3

Traffic Shifting (Canary Deployments)

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
  - reviews
  http:
  - route:
    - destination:
        host: reviews
        subset: v1
      weight: 90
    - destination:
        host: reviews
        subset: v2
      weight: 10

Traffic Mirroring

Mirror production traffic to a new version for testing. Mirrored traffic is fire-and-forget - responses are discarded.

Gateway - Ingress/Egress

An Istio Gateway configures a load balancer at the edge of the mesh. Combined with a VirtualService, it controls how external traffic enters the mesh.

🔑 Key Concepts

  • VirtualService: Routing rules - match conditions, traffic splitting, mirroring, retries, timeouts, fault injection
  • DestinationRule: Post-routing policies - subsets (versions), load balancing, connection pools, outlier detection
  • Gateway: Mesh boundary config - ingress/egress ports, TLS termination, host matching
  • Traffic shifting: Weight-based routing for canary deployments (90/10 → 50/50 → 0/100)
  • Traffic mirroring: Shadow traffic to new versions for testing without user impact
  • Header-based routing: Route specific users (e.g., end-user: jason) to different versions

4. Network Resiliency

Microservices architectures are inherently distributed, which means network failures are the norm. Istio provides resiliency features that protect services from cascading failures without application code changes.

Circuit Breaker

Circuit breakers prevent a failing service from overwhelming the system. Configured via DestinationRule using connectionPool (limits) and outlierDetection (ejection).

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 100
        http2MaxRequests: 1000
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
      maxEjectionPercent: 50

Retries

Automatic retries handle transient failures. Configure via VirtualService with control over attempts, per-try timeout, and retry conditions.

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: ratings
spec:
  hosts:
  - ratings
  http:
  - route:
    - destination:
        host: ratings
    retries:
      attempts: 3
      perTryTimeout: 2s
      retryOn: 5xx,gateway-error,connect-failure

Timeouts

Timeouts prevent requests from hanging indefinitely. Set at the VirtualService level, they apply to the entire request lifecycle including retries.

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
  - reviews
  http:
  - route:
    - destination:
        host: reviews
    timeout: 10s

Fault Injection

Test resiliency by deliberately introducing failures. Two types: delay (simulates latency) and abort (simulates HTTP errors).

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: ratings
spec:
  hosts:
  - ratings
  http:
  - fault:
      delay:
        percentage:
          value: 100.0
        fixedDelay: 7s
    route:
    - destination:
        host: ratings

Injects a 7-second delay on 100% of requests to ratings - tests how upstream services handle slow dependencies.

Outlier Detection

Tracks health of individual endpoints. When an endpoint exceeds the error threshold, it is temporarily ejected from the load balancing pool. Prevents a single bad pod from degrading the entire service.

🔑 Key Concepts

  • Circuit breaker: DestinationRule connectionPool (limits) + outlierDetection (ejection). Prevents cascading failures
  • Retries: VirtualService retries config. Control attempts, per-try timeout, and retry conditions
  • Timeouts: VirtualService timeout. Applies to entire request lifecycle including retries
  • Fault injection - delay: Simulate latency (e.g., 7s delay on ratings). Tests timeout and retry behavior
  • Fault injection - abort: Simulate HTTP errors (e.g., 503). Tests circuit breaker and fallback behavior
  • Outlier detection: Ejects unhealthy endpoints. Key params: consecutive5xxErrors, interval, baseEjectionTime, maxEjectionPercent

5. Security & Zero Trust

Istio implements a zero trust security model where no service is trusted by default, even within the cluster. Every request is authenticated, authorized, and encrypted - all transparently at the sidecar level.

mTLS - Mutual TLS

Istiod acts as a Certificate Authority, issuing SPIFFE-based X.509 certificates to every workload. mTLS mode is controlled by PeerAuthentication:

  • STRICT: Only mTLS traffic accepted. Non-mesh clients rejected.
  • PERMISSIVE: Accepts both mTLS and plaintext. Default - allows gradual mesh adoption.
  • DISABLE: No mTLS. Rarely used.
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT

AuthorizationPolicy

Controls which services can communicate. Three actions:

  • ALLOW: Explicitly permit matching requests. If any ALLOW exists, non-matching requests are denied.
  • DENY: Explicitly reject. Evaluated before ALLOW.
  • CUSTOM: Delegate to external provider (OPA, custom webhook).
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-productpage
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/default/sa/frontend"]
    to:
    - operation:
        methods: ["GET"]
        paths: ["/productpage", "/static/*"]

RequestAuthentication - JWT Validation

Validates JWTs on incoming requests. Specifies accepted issuers and JWKS URIs for signature verification.

apiVersion: security.istio.io/v1
kind: RequestAuthentication
metadata:
  name: jwt-auth
  namespace: default
spec:
  selector:
    matchLabels:
      app: productpage
  jwtRules:
  - issuer: "https://accounts.google.com"
    jwksUri: "https://www.googleapis.com/oauth2/v3/certs"

SPIFFE Identity Model

Every workload gets a SPIFFE ID: spiffe://cluster.local/ns/{namespace}/sa/{service-account}. Embedded in X.509 certificates, used for mTLS authentication and authorization policy evaluation. Enables identity federation across clusters.

🔑 Key Concepts

  • PeerAuthentication: Controls mTLS mode (STRICT/PERMISSIVE/DISABLE) per mesh, namespace, or workload
  • AuthorizationPolicy: L4/L7 access control with ALLOW, DENY, CUSTOM. DENY evaluated first
  • RequestAuthentication: JWT validation at mesh level. Specifies accepted issuers and JWKS URIs
  • SPIFFE: Workload identity: spiffe://trust-domain/ns/namespace/sa/service-account
  • Zero Trust pattern: deny-all default + explicit ALLOW rules = least-privilege networking
  • Certificate rotation: Istiod rotates workload certificates automatically (default 24h TTL)

6. Observability

One of Istio's most immediate benefits is deep observability without instrumenting application code. All traffic flows through Envoy sidecars, which automatically collect metrics, traces, and access logs for every request.

Kiali - Service Mesh Visualization

Kiali is the observability console for Istio. Real-time traffic graph showing service-to-service communication, request rates, error rates, and latency. Also validates Istio configuration and detects misconfigurations.

Distributed Tracing - Jaeger/Tempo

Istio generates trace spans for every request. Spans are sent to Jaeger, Zipkin, or Grafana Tempo. Important: Istio handles span creation at the proxy level, but applications must propagate trace headers (x-request-id, x-b3-traceid) for end-to-end correlation.

Metrics - Prometheus + Grafana

Envoy sidecars expose metrics in Prometheus format:

  • istio_requests_total - Request count by source, destination, response code
  • istio_request_duration_milliseconds - Latency histogram
  • istio_tcp_sent_bytes_total / istio_tcp_received_bytes_total - TCP volume

Access Logging

Configure via Telemetry CRD or MeshConfig. Logs include source/destination workload, response code, latency, and request metadata.

apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: mesh-default
  namespace: istio-system
spec:
  accessLogging:
  - providers:
    - name: envoy

🔑 Key Concepts

  • Kiali: Service mesh console - traffic graph, config validation, health monitoring
  • Distributed tracing: Jaeger/Tempo integration. Apps must propagate trace headers
  • Prometheus metrics: istio_requests_total, istio_request_duration_milliseconds - auto-collected
  • Grafana dashboards: Pre-built mesh overview, service, and workload dashboards in Istio addons
  • Access logging: Per-request logs via Telemetry CRD. Useful for debugging and audit
  • Addons install: kubectl apply -f samples/addons/ installs Kiali, Jaeger, Prometheus, Grafana
