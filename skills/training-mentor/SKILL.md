# Training Content Mentor

## Purpose
Generate a self-contained, visually clean HTML page that serves as a personal training portal for any technical topic. The output is a single .html file the user can open in any browser - no server needed.

## When to use
- User shares a topic list, syllabus, or table of contents and wants structured learning content
- User wants to prepare for a new technology, certification, or deep-dive
- User asks for a "study guide", "training page", or "learning portal" on a subject

## Content sourcing rules

### Curated bookmarks (priority source)
Before starting research, check if `~/.kiro/skills/training-mentor/references/bookmarks.md` exists. This file is generated by the `bookmark-curator` Skill and contains links the user personally saved. ALL links from this file are automatically "Important References" - no special marker needed in the .md, the source file itself is the marker. When a bookmark's tags match the study topic:
- Include it in the resources grid with a `⭐ Important Reference` badge (gold star + label, styled distinctly from regular links)
- Place curated bookmarks ABOVE web-searched links in the left column of the resources grid
- Use this HTML pattern for the badge: `<span class="badge-important">⭐ Important Reference</span>` with CSS: `.badge-important { background: #FFF3CD; color: #856404; padding: 2px 8px; border-radius: 4px; font-size: 0.75rem; font-weight: 600; margin-right: 6px; }`
- These take priority over web search results - they are pre-curated by the user

### Personal notes (priority source)
If you use a note-taking app (Notion, Evernote, Google Keep, Apple Notes, OneNote, Obsidian, etc.), search for pages matching the study topic. Personal notes from deep dives, customer engagements, and study sessions are high-value references.
- If matching notes are found, include them with a `📝 Personal Notes` badge
- Badge HTML: `<span class="badge-notes">📝 Personal Notes</span>` with CSS: `.badge-notes { background: #D4EDDA; color: #155724; padding: 2px 8px; border-radius: 4px; font-size: 0.75rem; font-weight: 600; margin-right: 6px; }`
- Place personal notes alongside curated bookmarks (above web-searched links)

### MCP-first research (mandatory)
Before generating ANY training content, ALWAYS query the AWS Knowledge MCP as the primary source:
- Use `mcp_knowledge_mcp_server_aws___search_documentation` to find official docs for each topic
- Use `mcp_knowledge_mcp_server_aws___read_documentation` to read and extract content from found pages
- Use search results to ground explanations in verified, current information
- Only fall back to web search for non-AWS topics or when MCP returns no results
- This prevents hallucinated URLs, outdated information, and fabricated technical details

1. **Official documentation first** - always prioritize vendor/project official docs (AWS docs, Kubernetes docs, CNCF docs, etc.)
2. **Trusted references only** - use well-known sources: official blogs, reputable tech publications, conference talks, RFCs, whitepapers
3. **YouTube videos** - search for high-quality videos from official channels, conference recordings (KubeCon, re:Invent, CNCF), and recognized educators. Use clickable thumbnail links (NOT iframes - they don't work on local `file://` HTML files).
4. **Recency matters** - prefer content from the last 12-18 months. Flag older content with a note if still relevant.
5. **Never fabricate URLs** - only include links you can verify exist. Use web search tools to find real, current URLs.
6. **Attribution** - every section must cite its sources with direct links
7. **Hands-on practice from official sources** - for each topic, search for practical content in official documentation:
   - **AWS:** Getting Started guides, Tutorials, How-To sections, Workshop Studio labs
   - **Kubernetes:** kubernetes.io/docs/tasks/ and kubernetes.io/docs/tutorials/
   - **CNCF projects:** Getting Started, Quickstart guides in official docs
   - **Other vendors:** Getting Started, How-To, User Guide practical sections
   - **GitHub repos:** aws-samples, awslabs, official project repos with examples/tutorials
   - **Interactive platforms:** KillerCoda scenarios, Play with Kubernetes
   - NEVER invent labs or exercises. Only curate existing hands-on content from trusted sources.
   - **Lab validation (mandatory):** Before including ANY hands-on lab, MUST fetch the URL and verify: (1) page loads with real content (not a redirect, 404, or stub), (2) content is freely accessible (no paywall, no paid subscription required), (3) content has actual step-by-step instructions (not just a README stub or empty repo), (4) for GitHub repos, check the README has real content (not just a license file). Remove any lab that fails these checks. NEVER include paywalled content without explicit disclosure.
   - **AI-generated labs:** When no real lab exists for a topic, the agent may create a hands-on exercise based on official documentation. These MUST be clearly marked with a warning badge: `<span class="badge-ai">⚠️ AI-Generated - Validate before use</span>` with CSS: `.badge-ai { background: #f8d7da; color: #721c24; padding: 2px 8px; border-radius: 4px; font-size: 0.75rem; font-weight: 600; margin-right: 6px; }`. AI-generated labs may contain hallucinated commands or incorrect parameters - validate them in a real cluster before relying on them.
   - Include with difficulty badge: L100 (intro), L200 (intermediate), L300 (advanced), L400 (expert)
   - **Difficulty badge rules:** Most modules should include labs from L100 through L300. L400 is reserved ONLY for advanced/expert modules (e.g., multi-cluster at scale, DR, platform engineering, advanced composition patterns). When in doubt, cap at L300.
   - Place in a dedicated Hands-On section in the HTML portal, after theory and before videos

## Research workflow
1. User provides topic list or syllabus
2. For each topic, use web search to find:
   - Official documentation page
   - 1-2 high-quality blog posts or tutorials
   - 1-2 YouTube videos (prefer official channels, conference talks, hands-on demos)
   - Any relevant GitHub repos or tools
3. Synthesize a concise explanation for each topic (not a copy-paste - a clear, structured summary)
4. Assemble into the HTML template

### YouTube video handling
- NEVER guess or fabricate YouTube video IDs - always obtain them from web search results
- Search patterns that work: `"topic" tutorial youtube site:youtube.com`, or check classcentral.com, GitHub repos, and blog posts that reference specific videos
- Confirmed video ID format: the 11-char string (e.g., `JLrR9RV9AFA`)
- If a video ID cannot be verified, omit the video rather than risk a broken link
- Wrap in `<details>` tags so they expand on-demand (better UX, collapsible)

#### YouTube embed limitation (file:// protocol)
YouTube blocks iframe embeds when the HTML is opened via `file://` protocol (local file). This is a YouTube security policy - `youtube-nocookie.com`, `referrerpolicy`, and other workarounds do NOT fix it. Do NOT waste time trying to fix iframe embeds for local files.

**Solution:** Instead of `<iframe>` embeds, use clickable thumbnail links that open YouTube in a new tab:
```html
<a href="https://www.youtube.com/watch?v={VIDEO_ID}" target="_blank" style="display:block;position:relative;max-width:560px">
  <img src="https://img.youtube.com/vi/{VIDEO_ID}/hqdefault.jpg" alt="Video title" style="width:100%;border-radius:8px">
  <span style="position:absolute;top:50%;left:50%;transform:translate(-50%,-50%);font-size:3rem">▶️</span>
</a>
```
This approach:
- Works on `file://` (thumbnails load fine, click opens YouTube)
- Shows a real preview thumbnail from YouTube's CDN
- Degrades gracefully if offline (broken image, but link still works)
- Keeps a clean, compact presentation inside the resources grid layout

## HTML output rules

### Structure
```text
Single .html file with:
├── Header (title, description, date generated)
├── Table of Contents (clickable, auto-generated from topics)
├── For each topic:
│   ├── Section header with anchor
│   ├── Concise explanation (2-4 paragraphs)
│   ├── Key concepts box (bullet points)
│   ├── Hands-on / Try it yourself (optional commands or exercises)
│   └── Resources grid (2-column layout):
│       ├── Left column: Official docs + Recommended reading links
│       └── Right column: YouTube video thumbnail cards (compact)
└── Footer (generation date, sources count)
```

### Visual design
- Clean, modern, readable - inspired by documentation sites
- Dark/light mode toggle
- Color scheme: neutral with blue accents (`#0073BB` for links, `#232F3E` for headers)
- Font: system font stack (`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, sans-serif`)
- Max width: 960px centered
- Responsive (works on mobile)
- Smooth scroll for TOC links
- Collapsible sections for long content
- Code blocks with syntax highlighting (inline CSS, no external deps)
- **Resources grid layout:** Each module ends with a 2-column CSS Grid (`grid-template-columns: 1fr 1fr`) - links on the left, compact video thumbnail cards on the right. Collapses to single column on mobile (`max-width: 700px`). This replaces the old stacked `<details>` approach for videos.
- **Video cards:** Small cards with 16:9 thumbnail, red play button overlay, and title below. Class `.video-card` with border-radius and hover shadow. Much cleaner than full-width thumbnails.

### Self-contained
- NO external CSS/JS dependencies (everything inline)
- YouTube videos use clickable thumbnail links (iframes don't work on `file://` protocol)
- All styles in `<style>` tag
- All interactivity in vanilla `<script>` tag
- File should work offline (YouTube thumbnails require internet; links open in browser)

## Quality checklist
- [ ] Every link is real and verified via web search
- [ ] YouTube video IDs confirmed from search results (never fabricated)
- [ ] Content is current (check dates)
- [ ] Explanations are clear, not just copy-pasted abstracts
- [ ] TOC matches all sections
- [ ] HTML is valid and renders correctly
- [ ] Dark/light mode works (including toggle persistence via localStorage)
- [ ] Mobile responsive
- [ ] File successfully saved to final destination

## File generation strategy

The HTML output is typically 500-800+ lines. A single tool call CANNOT handle this - you MUST chunk the writes.

### Chunked writing (critical)
- **First call** (`fsWrite`): Write `<!DOCTYPE>` through end of TOC (`</nav>`). This includes `<head>`, all CSS in `<style>` (including `.resources-grid`, `.video-card` classes), the header, and the table of contents.
- **One `fsAppend` per module**: Each module (`<section class="module">...</section>`) is one append call. Each module ends with a `<div class="resources-grid">` containing the 2-column layout (links-col + videos-col with video-cards). Keep the entire resources-grid inside the same append as its module.
- **Final `fsAppend`**: The last module (summary), `</div>`, `<footer>`, `<script>` (theme toggle + localStorage), and `</body></html>`.
- **Never try to write the entire HTML in a single call** - it will either fail silently, truncate, or hit payload limits.

### Destination strategy
1. **Build in the workspace** - `fsWrite` + `fsAppend` only work inside the workspace root.
2. **Copy to final destination** - use `cp` via bash to move the file to `~/Downloads/` or your preferred output folder.
3. **Clean up** - delete the temporary file from the workspace after confirming the copy succeeded.
4. **Naming convention** - `{topic-slug}-training.html` (lowercase, hyphenated)

### Editing existing HTML files
- NEVER use `sed` for surgical edits on large HTML files - it's fragile, hard to debug, and prone to partial replacements that corrupt the file.
- If a fix is needed, **regenerate the full file** using the same chunked write strategy. It's faster and safer than debugging broken sed commands.
- Keep the chunked approach modular (one section per append) so regeneration is straightforward.

## Trail Strategy (large topics)

Every topic gets its own folder under the training output directory. This is the standard pattern - no exceptions.

```text
~/training-portals/{topic-slug}/
├── index.html                    (hub page - always present)
├── {topic-slug}-training.html    (theory portal)
├── {topic-slug}-labs.html        (hands-on labs portal)
└── (additional portals if topic is split into sub-trails)
```

For topics with sub-trails (like GitOps with prerequisites/fundamentals/advanced):
```text
~/training-portals/gitops/
├── index.html                           (trail hub linking all portals)
├── gitops-prerequisites-training.html
├── gitops-argocd-training.html
├── gitops-at-scale-training.html
└── gitops-labs.html                     (shared labs for the entire trail)
```

Everything lives in the same folder - index.html alongside the portal HTMLs. Links between files are relative (no `../`). This keeps each topic self-contained and portable.

### index.html structure
- Same visual style as portals (dark/light toggle, AWS color scheme)
- Trail title and description
- Ordered list of portals with: title, description, module count, status badge (not started / in progress / completed)
- Generation date and total module count

### When to split
- 8+ modules -> split into 2-3 portals by logical grouping
- Clear prerequisite chain -> split into levels (prerequisites -> fundamentals -> advanced)
- Mixed domains -> split by domain (e.g., ArgoCD vs Argo Rollouts)

### When NOT to split
- 7 or fewer modules -> single portal
- All modules are tightly coupled -> single portal

## Link Tracker

File: `~/.kiro/skills/training-mentor/data/link-tracker.json`

Tracks which links have been included in portals and which have been consumed.

```json
{
  "portals": [
    {
      "file": "gitops-argocd-training.html",
      "topic": "GitOps ArgoCD Fundamentals",
      "generatedAt": "2026-03-11",
      "status": "not-started",
      "links": ["https://url1", "https://url2"]
    }
  ],
  "consumed": [
    {
      "url": "https://...",
      "consumedAt": "2026-04-15",
      "portal": "gitops-argocd-training.html"
    }
  ]
}
```

### Consumption flow
1. When generating a portal, register it and all its links in `link-tracker.json`
2. Before including a link in a new portal, check if it's already in `consumed` - skip it
3. User marks consumption per portal ("terminei o gitops-argocd") -> all links in that portal move to consumed, portal status = completed

- Path: `{your-bookmarks-data-path}/bookmarks-data.json`
- Fed by: bookmark-curator (from Firefox favorites) AND learning-curator (from open tabs triage)

When generating a portal:

## Output location

Multi-portal trails add sub-portals in the same folder.

## Companion Skills

- `bookmark-curator` (agent): feeds curated links into `bookmarks-data.json` from Firefox favorites. Runs autonomously.
- `learning-curator`: feeds triaged links into `bookmarks-data.json` from open browser tabs. Interactive.
- `challenge-mentor`: generates unguided troubleshooting challenges based on training portal content. The natural next step after completing labs.

### Challenge Mode Section (MANDATORY in labs portals)

Every labs portal MUST end with a "Challenge Mode" section before the footer. This links the guided labs to the unguided challenge-mentor skill, creating the learning progression: **theory -> guided practice -> unguided challenge**.

HTML pattern:
```html
<section class="lab" id="challenge-mode">
<h2>🎯 Challenge Mode</h2>
<div style="border-left:4px solid #ff9800;padding:16px 20px;margin:16px 0;background:var(--warn-bg);border-radius:0 8px 8px 0;color:var(--warn-text)">
<h4>Completed the guided labs?</h4>
<p>Test your knowledge without a guide. Activate <code>#challenge-mentor</code> in chat and request challenges about <strong>[TOPIC]</strong>.</p>
<p>The mentor will generate new scenarios in the same domain - variations you didn't see in the labs, with different root causes and no step-by-step guide.</p>
<p style="margin-top:12px"><strong>Example:</strong> "I want [TOPIC] challenges Lv300"</p>
</div>
</section>
```

Replace `[TOPIC]` with the portal's topic (e.g., "Istio troubleshooting", "NGINX migration", "Crossplane compositions").

## Lab 0: Environment Provisioning Pattern (MANDATORY)

Every labs portal MUST start with a **Lab 0** that provisions the complete environment via IaC (Terraform or CloudFormation). The user should go from zero to a fully functional environment with a single `terraform apply`.

### Design Principles

1. **IaC-first:** Lab 0 delivers a Terraform (preferred) or CloudFormation template that provisions everything needed for the labs. Prerequisites are limited to: AWS CLI, Terraform, kubectl.
2. **Legacy environment = automated:** The IaC deploys the "before" state - the legacy/baseline environment that subsequent labs will modify, migrate, or troubleshoot. After `terraform apply`, the environment is functional and ready.
3. **Corrections/improvements = manual:** The actual learning happens in Labs 1-N where the user makes changes by hand (kubectl, helm, manifest edits). Lab 0 is setup, not learning.
4. **Troubleshooting labs = broken on purpose:** For troubleshooting scenarios, the IaC can provision a second cluster or namespace with intentional misconfigurations. The user's job is to find and fix them.
5. **Cleanup included:** Lab 0 always ends with a cleanup section (`terraform destroy`) and the cleanup is also referenced at the end of the labs portal.
6. **Self-guided completeness (HARD RULE):** Every lab must be executable from start to finish without external knowledge. If a lab needs a specific environment state (broken cluster, pre-deployed app, specific config), that state MUST be created within the lab itself or referenced to a specific prior lab step. No "assume X exists" - either Lab 0 provisions it, or the lab has a setup step that creates it.

### IaC Source Priority

1. **Official aws-samples/aws-ia repos** - Use existing Terraform patterns from `aws-ia/terraform-aws-eks-blueprints/patterns/` or `aws-samples/` repos. These are maintained, tested, and follow AWS best practices.
2. **EKS Blueprints addons** - For specific tools (Istio, ingress-nginx, ArgoCD), check if `terraform-aws-eks-blueprints-addons` has a ready-made addon.
3. **eksdemo** - [`awslabs/eksdemo`](https://github.com/awslabs/eksdemo) is an "easy button" CLI for EKS demos/labs. Installs 70+ apps with single commands. Faster than Terraform for demo/lab environments.
4. **eksctl quickstart** - Lightweight alternative with `eksctl create cluster` + config file. Simpler but less reproducible.
5. **Custom Terraform** - Only create custom IaC when no official pattern exists. Mark with `⚠️ AI-Generated` badge and note that it needs validation.

### What Lab 0 Provisions (typical)

- VPC with public/private subnets
- EKS cluster with managed node group (appropriate instance type for the topic)
- Required IAM roles and policies (IRSA/Pod Identity)
- Topic-specific controllers/tools (e.g., AWS LBC, Istio, ArgoCD)
- Sample application deployed and accessible
- Ingress/Gateway resources configured and functional

### Multi-Cluster for Troubleshooting

When labs include troubleshooting scenarios:
- Provision 2 clusters: `healthy` (reference) and `broken` (intentional misconfigs)
- Or provision 1 cluster with 2 namespaces: `working` and `broken`
- Document what's broken in a sealed section (expandable `<details>` tag) so the user can check after attempting the fix

### Template Structure

```text
Lab 0: Provision the Environment
├── Objective (what gets deployed)
├── Prerequisites (AWS CLI, Terraform, kubectl - nothing else)
├── Step 1: Clone/download the Terraform config
├── Step 2: terraform init + plan + apply
├── Step 3: Configure kubectl
├── Step 4: Deploy sample application (if not in Terraform)
├── Step 5: Validate everything works
├── Validation checklist
├── Cleanup section (terraform destroy)
└── References (IaC source repo, official docs)
```
